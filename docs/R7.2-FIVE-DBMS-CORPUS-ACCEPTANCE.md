# R7.2 — Five-DBMS Legacy Corpus Acceptance

## Purpose

R7.2 validates the full legacy canonical corpus across Oracle, PostgreSQL, Db2 for z/OS,
SQL Server, and MySQL without weakening the project No-Guess policy.

The source canonical corpus is immutable. Evidence-backed numeric recovery is materialized into a
separate derived canonical corpus and that derived corpus is then consumed by the generic
`CanonicalJsonDirectoryToDdlIT` runner.

## Raw SAFE gate observation (2026-08-25)

Input corpus: 5,321 snapshots / 97,261 columns.

- Oracle: 5,294 generated, 2 warning-bearing, 25 mapping-blocked.
- PostgreSQL: 5,321 generated, 0 blocked.
- Db2/zOS: 3,813 generated, 1,508 mapping-blocked.
- SQL Server: 3,823 generated, 1,498 mapping-blocked.
- Snapshot failures: 0.
- Canonical errors: 0.
- Output-name collisions: 38, all resolved by the collision-safe allocator.

The dominant raw blockers are the same canonical exact-numeric metadata gap already addressed by
R7.1 evidence recovery: 1,485 snapshots are blocked in both Db2/zOS and SQL Server by NUMBER values
with no explicit precision. This is a canonical-evidence problem, not two independent dialect bugs.

## R7.2 preparation change

`MySqlFinalRecoveryGenerationIT` now supports two optional properties:

- `schemaforge.mysql.final.recoveredSnapshotDir`
- `schemaforge.mysql.final.cleanRecoveredSnapshots` (default `true`)

When `recoveredSnapshotDir` is supplied, the runner writes one derived `*.schema.json` for every
successfully loaded source snapshot after applying the same DB2 metadata, historical consensus, and
confirmed R7/R8/R10 evidence used by the final recovery flow.

The derived snapshot:

- preserves source identity;
- preserves the original snapshot/model/parser version provenance;
- carries only evidence-backed in-memory type recovery;
- is written outside the source corpus;
- never mutates the original canonical JSON.

The gate requires every loaded source snapshot to be accounted for as either a successfully written
derived snapshot or a write failure, and requires zero derived-snapshot write failures when the
feature is enabled.

`Recovered snapshot write failures = 0`.

## Step 2 — observe the recovered SAFE four-DBMS gate

The first recovered-corpus pass is intentionally observational. Residual hard blockers are expected
because No-Guess unresolved evidence remains in the corpus. Do not use `failOnErrors=true` until the
post-recovery per-platform baselines have been frozen.

```bat
set "SCHEMAFORGE_NUMERIC_MAPPING_STRATEGY=SAFE"

mvnw.cmd ^
  -Dtest=CanonicalJsonDirectoryToDdlIT ^
  -Dschemaforge.snapshot.ddl.inputDir="D:\Sample-Docs-Scripts\SchemaForge-Recovered-Canonical-R7.2" ^
  -Dschemaforge.snapshot.ddl.outputDir="D:\Sample-Docs-Scripts\SchemaForge-R7.2-RECOVERED-SAFE-4DBMS" ^
  -Dschemaforge.snapshot.ddl.platforms=oracle,postgresql,db2zos,sqlserver ^
  -Dschemaforge.snapshot.ddl.expectedMinSnapshots=5321 ^
  -Dschemaforge.snapshot.ddl.failOnErrors=false ^
  -Dschemaforge.snapshot.ddl.failOnWarnings=false ^
  -Dschemaforge.snapshot.ddl.cleanOutput=true ^
  test
```

The output of Step 2 is used to freeze the first evidence-backed per-platform R7.2 acceptance
baselines. A later strict gate must fail on regression below those baselines, unexpected generation
failures, snapshot-read failures, or new canonical errors; it must not require guessed resolution of
explicit hard blockers.
