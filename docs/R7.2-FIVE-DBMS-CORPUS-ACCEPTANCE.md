# R7.2 — Five-DBMS Legacy Corpus Acceptance

## Purpose

R7.2 validates the full legacy canonical corpus across Oracle, PostgreSQL, Db2 for z/OS,
SQL Server, and MySQL without weakening the project No-Guess policy.

The source canonical corpus is immutable. Evidence-backed numeric recovery is materialized into a
separate derived canonical corpus and that derived corpus is then consumed by the generic
`CanonicalJsonDirectoryToDdlIT` runner.

## Raw SAFE gate observation (2026-08-25)

Input corpus: 5,321 snapshots / 97,261 columns.

- Oracle: 5,294 generated, 2 warning-bearing, 25 mapping-blocked.
- PostgreSQL: 5,321 generated, 0 blocked.
- Db2/zOS: 3,813 generated, 1,508 mapping-blocked.
- SQL Server: 3,823 generated, 1,498 mapping-blocked.
- Snapshot failures: 0.
- Canonical errors: 0.
- Output-name collisions: 38, all resolved by the collision-safe allocator.

The dominant raw blockers are the same canonical exact-numeric metadata gap already addressed by
R7.1 evidence recovery: 1,485 snapshots are blocked in both Db2/zOS and SQL Server by NUMBER values
with no explicit precision. This is a canonical-evidence problem, not two independent dialect bugs.

## R7.2 preparation change

`MySqlFinalRecoveryGenerationIT` now supports two optional properties:

- `schemaforge.mysql.final.recoveredSnapshotDir`
- `schemaforge.mysql.final.cleanRecoveredSnapshots` (default `true`)

When `recoveredSnapshotDir` is supplied, the runner writes one derived `*.schema.json` for every
successfully loaded source snapshot after applying the same DB2 metadata, historical consensus, and
confirmed R7/R8/R10 evidence used by the final recovery flow.

The derived snapshot:

- preserves source identity;
- preserves the original snapshot/model/parser version provenance;
- carries only evidence-backed in-memory type recovery;
- is written outside the source corpus;
- never mutates the original canonical JSON.

The gate requires every loaded source snapshot to be accounted for as either a successfully written
derived snapshot or a write failure, and requires zero derived-snapshot write failures when the
feature is enabled.

## Step 2 observed recovered SAFE baseline (2026-08-25)

Recovered canonical input remained structurally identical to the source corpus: 5,321 tables,
97,261 columns, 4,514 primary keys, 1,325 foreign keys, 3,233 indexes, and 14,518 defaulted columns.
There were zero snapshot failures and zero canonical errors.

| Platform | Successful scripts | Warning-bearing | Mapping-blocked | Generation failed |
|---|---:|---:|---:|---:|
| Oracle | 5,296 | 2 | 25 | 0 |
| PostgreSQL | 5,321 | 0 | 0 | 0 |
| Db2/zOS | 4,693 | 0 | 628 | 0 |
| SQL Server | 4,703 | 0 | 618 | 0 |

Compared with the raw canonical corpus, the evidence-backed overlay newly unblocked exactly 880
snapshots for Db2/zOS and exactly 880 snapshots for SQL Server. Oracle and PostgreSQL remained
unchanged, as expected.

Residual blocking mapping codes are frozen as follows:

- Oracle: `ORACLE_DECIMAL_PRECISION_UNSUPPORTED` only.
- PostgreSQL: none.
- Db2/zOS: `DB2_NUMBER_PRECISION_REQUIRED`, `DB2_DECIMAL_PRECISION_UNSUPPORTED` only.
- SQL Server: `SQLSERVER_EXACT_NUMERIC_PRECISION_REQUIRED`, `SQLSERVER_DECIMAL_PRECISION_UNSUPPORTED` only.

The cross-dialect blocker analysis shows 598 snapshots blocked in common across MySQL, Db2/zOS, and
SQL Server because exact canonical NUMBER precision remains unavailable. These are evidence gaps and
must remain blocked under the No-Guess policy. Target-specific precision ceilings explain the small
remaining differences: Db2/zOS DECIMAL is limited to precision 31, while Oracle and SQL Server permit
up to precision 38. MySQL also retains one ROWID physical-artifact review blocker that does not apply
to the four-DBMS runner.

The 62 output-name collisions observed in the recovered run were all resolved by
`CollisionSafeScriptTargetAllocator`; no target was written twice and collisions are not acceptance
failures.

## Step 3 — strict SAFE regression gate

`CanonicalJsonDirectoryToDdlIT` now supports an acceptance mode that freezes the observed baseline
without requiring hard blockers to be guessed away.

Set `schemaforge.snapshot.ddl.failOnRegression=true` and provide, for every selected platform:

- `schemaforge.snapshot.ddl.expectedMinSuccessful.<platform>`
- `schemaforge.snapshot.ddl.expectedMaxBlockedMapping.<platform>`
- `schemaforge.snapshot.ddl.expectedMaxWarningScripts.<platform>`
- `schemaforge.snapshot.ddl.allowedBlockingCodes.<platform>` (optional/empty when no blocker is allowed)

The regression gate also requires zero snapshot failures, zero canonical errors, zero SQL generation
failures, zero generated scripts with validation errors, and exact per-platform corpus accounting.

```bat
set "SCHEMAFORGE_NUMERIC_MAPPING_STRATEGY=SAFE"

mvnw.cmd ^
  -Dtest=CanonicalJsonDirectoryToDdlIT ^
  -Dschemaforge.snapshot.ddl.inputDir="D:\Sample-Docs-Scripts\SchemaForge-Recovered-Canonical-R7.2" ^
  -Dschemaforge.snapshot.ddl.outputDir="D:\Sample-Docs-Scripts\SchemaForge-R7.2-RECOVERED-SAFE-STRICT" ^
  -Dschemaforge.snapshot.ddl.platforms=oracle,postgresql,db2zos,sqlserver ^
  -Dschemaforge.snapshot.ddl.expectedMinSnapshots=5321 ^
  -Dschemaforge.snapshot.ddl.failOnErrors=false ^
  -Dschemaforge.snapshot.ddl.failOnWarnings=false ^
  -Dschemaforge.snapshot.ddl.failOnRegression=true ^
  -Dschemaforge.snapshot.ddl.expectedMinSuccessful.oracle=5296 ^
  -Dschemaforge.snapshot.ddl.expectedMaxBlockedMapping.oracle=25 ^
  -Dschemaforge.snapshot.ddl.expectedMaxWarningScripts.oracle=2 ^
  -Dschemaforge.snapshot.ddl.allowedBlockingCodes.oracle=ORACLE_DECIMAL_PRECISION_UNSUPPORTED ^
  -Dschemaforge.snapshot.ddl.expectedMinSuccessful.postgresql=5321 ^
  -Dschemaforge.snapshot.ddl.expectedMaxBlockedMapping.postgresql=0 ^
  -Dschemaforge.snapshot.ddl.expectedMaxWarningScripts.postgresql=0 ^
  -Dschemaforge.snapshot.ddl.expectedMinSuccessful.db2zos=4693 ^
  -Dschemaforge.snapshot.ddl.expectedMaxBlockedMapping.db2zos=628 ^
  -Dschemaforge.snapshot.ddl.expectedMaxWarningScripts.db2zos=0 ^
  -Dschemaforge.snapshot.ddl.allowedBlockingCodes.db2zos=DB2_NUMBER_PRECISION_REQUIRED,DB2_DECIMAL_PRECISION_UNSUPPORTED ^
  -Dschemaforge.snapshot.ddl.expectedMinSuccessful.sqlserver=4703 ^
  -Dschemaforge.snapshot.ddl.expectedMaxBlockedMapping.sqlserver=618 ^
  -Dschemaforge.snapshot.ddl.expectedMaxWarningScripts.sqlserver=0 ^
  -Dschemaforge.snapshot.ddl.allowedBlockingCodes.sqlserver=SQLSERVER_EXACT_NUMERIC_PRECISION_REQUIRED,SQLSERVER_DECIMAL_PRECISION_UNSUPPORTED ^
  -Dschemaforge.snapshot.ddl.cleanOutput=true ^

```

This strict SAFE run is the R7.2 acceptance gate. A future improvement may increase successful counts
or reduce blockers without changing this command; any regression below the frozen floor or above the
frozen blocker ceiling fails immediately.
