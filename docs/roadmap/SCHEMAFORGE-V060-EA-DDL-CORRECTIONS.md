# SchemaForge V0.6.0 — EA / Legacy Word DDL correction and naming contract

Date: 2026-10-24. Backend / DDL patch based on full V0.5.9; React Console remains V0.5.9.

## Decisions fixed by product owner

- **Db2 z/OS**: `VARCHAR(n) FOR BIT DATA` is intentional and MUST stay unchanged.
- **Oracle**: `NVARCHAR2(n CHAR)` (and `NVARCHAR2(n BYTE)`) MUST become `NVARCHAR2(n)`; the same implicit national semantics apply to `NCHAR(n)`.
- **JSON CHECK**: `IS JSON` is a predicate, not an undeclared column. Never invent target SQL where no supported equivalent is known; report explicit unsupported constraints.
- **PostgreSQL numeric identity**: `NUMERIC(p,0) GENERATED BY DEFAULT AS IDENTITY` is invalid. Keep the full numeric domain with `NUMERIC(p,0) DEFAULT nextval('schema.seq_table')` and create the named sequence before the table. Do not coerce the COLUMN `NUMBER(19,0)` to signed BIGINT. Native integer identity remains supported. PostgreSQL sequences themselves still use PostgreSQL's built-in sequence integer range; the declared column remains NUMERIC(19,0), but a sequence is not proof that every theoretical 19-digit positive value can be generated.
- **Object names**: PK, UK, FK, CHECK, and standalone INDEX use `LogicalObjectNamingPolicy` + `PhysicalObjectNamePolicy` exclusively, regardless of Word / EA original names. Existing policy is frozen, not replaced.

## JSON profile applicability

| DBMS | Behavior for simple `COLUMN IS JSON` |
|---|---|
| Oracle | `column IS JSON` |
| PostgreSQL **16+** | `column IS JSON` — check server version before running |
| SQL Server | `ISJSON(column) = 1` |
| MySQL | `JSON_VALID(column) = 1` |
| MariaDB | `JSON_VALID(column) = 1` |
| Db2 LUW | `CHECK-JSON-001`: not emitted, unsupported without an approved, version-specific predicate |
| Db2 z/OS | `CHECK-JSON-001`: not emitted, unsupported without an approved, version-specific predicate |

This release translates **only simple** `IS [NOT] JSON` predicates. Mixed/nested Oracle JSON syntax is left as an explicit unsupported CHECK; it is never copied to a dialect that cannot guarantee syntax validity. Preserve the original expression in Canonical JSON.

These vendor translations can differ subtly in JSON scalar acceptance and null behavior. Verify with live target DBMS and application data before migration/deployment.

## Manifest accuracy

EA `manifest.json` has new `extensions.ddlConstraintCoverage` keyed by DBMS name. Each platform records:

- `declared`: total source CHECK constraints;
- `renderable`: checks whose syntax passes current renderer and reference checks;
- `unsupportedJson`: IS JSON predicates without an approved target mapping;
- `unknownColumnReferences`: CHECKs with invalid column references.

**Important**: this is a deterministic *declared-vs-renderable policy* count, not proof that SQL ran on a database. The reported `renderable` count verifies known expression families (including JSON) and absence of unknown-column identifiers; it is not a complete SQL grammar validator. `artifactOutcomes.blocked` still counts whole blocked artifact files, **not individual CHECK clauses**. A manifest `requestStatus=SUCCESS` can include `unsupportedJson>0` when the DDL file was produced with an explicit unsupported CHECK comment. UI/report consumers must show the separate constraint coverage.

## PostgreSQL numeric identity consistency beyond CREATE DDL

- The schema-diff engine and XLSX comparison use the per-column named-sequence policy and the same deterministic physical sequence identifier.
- PostgreSQL catalog defaults such as `nextval('app.seq_table'::regclass)` are treated as equivalent to canonical sequence-backed logical IDENTITY, avoiding spurious ALTER_IDENTITY/ALTER_DEFAULT results.
- An ADD COLUMN migration requiring a *new* PostgreSQL sequence-backed NUMERIC identity is **BLOCKED for DBA review**, not emitted as invalid SQL; the operational migration must arrange sequence creation, default and privileges/ownership atomically.
- Ordinary PostgreSQL INTEGER/BIGINT/SMALLINT identity columns retain native IDENTITY SQL.

## Windows installation

1. Stop Spring Boot and Vite.
2. Back up `D:\Projects\schema-forge-v4` (and live H2 separately if required).
3. If installed version is **V0.5.9**, extract the `V060-DELTA-FLAT.zip` at project root. Otherwise use `V060-FULL.zip`, following the usual clean-source workflow.
4. In Command Prompt, run:

```
cd /d D:\Projects\schema-forge-v4
call scripts\accept-ea-ddl-v060.cmd
mvnw.cmd spring-boot:run
```

The script includes the new real-XMI and numeric sequence regression plus existing Oracle, PostgreSQL, Schema Diff, Migration, XLSX Comparison, Db2 z/OS, naming and Legacy Word tests. For wider regression run `mvnw.cmd test` in an isolated, reproducible environment. Run a live Oracle and PostgreSQL 16+ deployment of a **test schema** before deploying generated scripts.

## Safety / continuity

- No H2 data, passwords, JDBC host defaults, React assets, Glossary statuses, or connection management changed in V0.6.0.
- All seven DBMS remain available. Canonical model schema and source EA parser remain unchanged.
- A successful ZIP/DDL generation still does not mean SQL has been executed on live databases. Unsupported checks are preserved as explicit diagnostics only.
- This acceptance is offline: 74 Java 21 regression methods using a lightweight offline assertion runner plus real XMI generation passed locally (25 DDL / naming / identity, 49 migration / diff); full Maven/Spring Boot/DBMS live acceptance remains pending on Windows.
