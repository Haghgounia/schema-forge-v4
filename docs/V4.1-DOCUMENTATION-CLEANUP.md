# SchemaForge v4.1 Documentation and Cleanup

## Scope

This maintenance release documents the current Java codebase without changing runtime behavior, REST contracts, schema models, SQL generation rules, or package structure.

## Documentation

- Every top-level production and test type now has class-level English JavaDoc.
- Newly added JavaDoc states the type's purpose and, where relevant, its architectural boundary.
- Domain types are documented as database-independent canonical model elements.
- Dialect types are documented as database-specific components that must not mutate the canonical model.
- Test JavaDoc records the behavior or regression boundary protected by the test.

## Deprecated types

The following legacy types remain in source for compatibility but are marked for later removal:

1. `Phase1Application`
   - Legacy offline command-line entry point.
   - Superseded by `SchemaForgeApiApplication` and the REST workflow.
2. `ApplicationDialectSelectionTest`
   - Tests the command-line option path of the deprecated application.
3. `Phase1PipelineTest`
   - Legacy end-to-end phase-one pipeline test.
   - Superseded by service, REST, Word regression, and EA regression tests.

No deprecated type was deleted in this release.

## Cleanup

- Removed trailing whitespace from Java sources.
- Normalized Java source files to end with one newline.
- Preserved public APIs, file naming, output structure, and generation behavior.

## Refactoring assessment

A large refactoring is intentionally deferred. Oracle, PostgreSQL, Word, EA XML, comparison workbooks, and per-table REST output are working capabilities and should not be destabilized immediately before adding new database dialects.

Before Db2 for z/OS, only focused changes are recommended:

- introduce the new dialect through existing extension points;
- avoid duplicated switch statements;
- extract only code that must be shared by three or more dialects;
- keep the canonical schema model database-independent;
- add regression tests before modifying shared generation paths.

A broader architectural refactoring should be considered after Db2 z/OS, SQL Server, and MySQL behavior is known.
