# R7.10 EA FK Association Recovery

## Problem

Some native Enterprise Architect XMI exports contain a stale, truncated, or otherwise
inconsistent FK role name on the source `AssociationEnd`. The actual FK operation on
the source table remains valid and the association still carries the source/target
table ids and column mapping.

Previously SchemaForge indexed FK associations only by:

`source-table-id + AssociationEnd.name`

When `AssociationEnd.name` differed from `UML:Operation.name`, the FK operation could
not find its association and the FK was silently omitted from the canonical model.

## Recovery contract

1. Exact source operation-name matching remains the primary path.
2. If the source operation name is inconsistent, SchemaForge uses the authoritative
   association structure as a fallback:
   - source table id (or source table name fallback),
   - FK stereotype,
   - ordered source column mapping.
3. Recovery is accepted only when those source columns identify exactly one FK
   operation on the source table.
4. Ambiguous matches remain fail-closed and are reported as recovery warnings.
5. Recovered FKs retain the canonical FK operation name from the table operation.
6. A recovered mismatch is recorded in schema metadata as
   `EA_FK_ASSOCIATION_OPERATION_MISMATCH_RECOVERED`.

## Real-file verification

Against the original `Final_4.xml` supplied during R7.10 validation:

- Tables: 50
- FK operations: 56
- FK associations: 56
- Previously name-mismatched associations: 44
- Foreign keys recovered after fix: 56 / 56
- `EA_FK_ASSOCIATION_NOT_FOUND`: 0
- `DEPOSIT_PRODUCT_ALLOWED_TERM`: 1 FK
  - `FK_DEPOSIT_PRODUCT_AL_1`
  - `TERM_RULE_ID -> DEPOSIT_PRODUCT_TERM_RULE.TERM_RULE_ID`
